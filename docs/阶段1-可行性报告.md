# REDcoLAB 阶段 1 技术可行性报告

- 项目中文名：红红子 LAB
- 项目英文名：REDcoLAB
- 目标环境：Windows 版 CLIP STUDIO PAINT Ver. 5.0（本机实测 5.0.4）
- 报告状态：**阶段 1 结论已完成；尚未开始写任何插件代码**
- 报告日期：2026-10-15
- 一句话结论：**官方 SDK 只允许开发「滤镜插件」，四项需求中只有「一键灰度」落在允许范围内；「原生导航器扩展」与「独立叠加剪切蒙版」在官方接口上无法实现，停止开发；「统一控制面板」只能实现为滤镜对话框 + 设置持久化，不能做成常驻停靠面板。**

## 3. 官方允许的插件类型：只有滤镜插件

【官方确认】Celsys 官网「プラグイン/SDK」页原文（要点）：

> CLIP STUDIO PAINT EX は…プラグイン機構を搭載しています。「CLIP STUDIO PAINT SDK」をWebサイトから入手して、どなたでも PAINT EX 用の**フィルタープラグイン**の開発を行えます。
> ※iPad版はフィルタープラグインの追加はできません。

【官方确认】SDK 使用许可契约书第 1 条对「フィルタープラグイン」的定义：

> CLIP STUDIO PAINT EX に新たな**フィルター機能**を追加するための、CLIP STUDIO PAINT EX の実行プログラム上でのみ動作するプラグインソフトウェア。

也就是说，官方口径里 **SDK 只能产出「滤镜」这一种形态**，没有第二种。

【官方确认】官方「要望・不具合ボード」2013 年 SDK 需求帖（ID 38765，赞成 24）里，用户原始陈述与 Celsys 场景完全一致：

> 利用できる範囲も「フィルタ」に限られ、例えば編集メニューの何かを拡張するといったレイヤーの設定や素材の貼り付けといった動作をSDKで記述することは難しいと思います。
> （当前能做的插件范围被限制，连「扩展编辑菜单里的某项」「设置图层」「粘贴素材」这类操作都很难用 SDK 实现。）

回帖者更进一步请求「实时处理」（笔压/坐标加工）与开放插件规格。该板 **2019-11-28 已停止收件**，此后无新增能力。

【官方确认】**官方插件商店现有的全部条目，无一例外都是滤镜**：色ムラ、流線、集中線、レトロフィルタ、自動影色指定、指定色を置換、加筆、ピクセレート水晶、α値レベル補正、Layer3D、HSV帯域補正、グロー、レンズブラー、ドロップシャドウ、**グレイスケール化**、超解像X2、二値誤差拡散……（节选，全表见 https://www.clip-studio.com/clip_site/download/clipstudiopaint/cspplugin ）

**没有一个是：导航器扩展、图层关系管理、常驻面板。**

### 3.1 一个必须先告诉你的重要发现

【官方确认】官方商店里已经有一个**免费**插件「**グレイスケール化**」（开发者 wotakun，描述：「カラー作品を複数の方式でグレイスケール化できます」= 可用多种方式把彩色作品灰度化）。

这意味着你的功能 B **并不是空白市场**，而且它正是「滤镜插件能做到的极限形态」。我仍会按你的要求做 REDcoLAB 版灰度（因为你可以自己控制算法、参数与流程），但你需要知道：这部分的价值在于「可控与集成」，而不是「CSP 做不到」。

### 3.2 滤镜插件的能力边界（据官方证据与第三方实录归纳）

| 能不能做 | 说明 | 依据 |
|---|---|---|
| 拿到执行目标图层的像素并改写 | 是。RGB/Alpha 级处理 | 【官方确认】商店描述中多次出现「ラスターレイヤーに描画されている画像の色を…」；「α値を変更しません」等说明证明插件可读写 Alpha |
| 提供自己的参数对话框 | 是（滤镜模态对话框） | 【第三方实测】SDK 样例工程 `HSV` 可在 `FilterPlugin\ProjectWin` 用 VS 构建，产物 `HSV.cpm` 放入插件目录后，滤镜菜单出现新项并有对话框 |
| 常驻停靠面板 | **否** | 【官方确认】SDK 定位为「追加滤镜功能」；商店全部插件均为随取随用的滤镜 |
| 注册全局快捷键 | **否**（快捷键只能由 CSP 自身的修饰键/快捷键设置分配） | 【官方确认】SDK 无任何入口注册快捷键；商店插件均无此能力 |
| 访问图层树 / 蒙版 / 剪切关系 | **否** | 【官方确认】契约书定义限定为「追加滤镜功能」；2013 要望帖明确「レイヤーの設定…は難しい」 |
| 读写 CSP 的视图状态（缩放/平移） | **否** | 【官方确认】契约书无此类授权；无任何公开 API |
| 知道「当前选了哪个图层」 | **否**，插件只知道「宿主把哪张图交给它处理」 | 【推测】基于契约定义与滤镜触发时机推断，**待真机验证** |

## 4. 四项需求逐条评估（对应阶段 1 要求的可行性表）

### 功能 A：CSP 原生导航器实时投影

**判定：不可行 —— 当前技术路线无法实现，暂停开发（按你第七条的要求处理，不找替代品顶替）。**

**缺失的能力与对应证据：**

1. 官方 SDK 只能产出滤镜插件（§3 全部证据）；
2. 滤镜插件的调用时机是「用户执行滤镜命令」的那一次，处理对象是「宿主交给它的图层像素」；它**没有**任何可注册的「画布内容变化通知」入口 —— 因此不存在事件驱动的更新来源；
3. SDK 不提供画布缩放/平移/视图状态的读取接口，也不提供导航器刷新机制；
4. 契约书第 1 条把插件定义死为「追加滤镜功能」，第 8 条第 1 项还禁止用 SDK 做「独自または派生の開発ツール」（自研或派生的开发工具），把绕过设计意图的空间也封住了；
5. 官方要望板上针对「插件能做实时处理」的请求没有任何落地记录。

**我没有做的事（明确声明）：**

- 没有写任何屏幕截图 / 桌面捕获 / 窗口捕获 / 录屏 / 定时截屏轮询代码；
- 没有用独立预览窗口伪装成「导航器扩展」；
- 没有读取 CSP 内存或调用非公开接口去挖画面数据。

这四条都是你明令禁止的，我一条都不会碰。

**唯一还值得你决定的合法路径：根本不是插件。** CSP 原生导航器本身已经实时显示画布（这是它的既有功能）。如果你的真实诉求是「低开销地实时看画布」，那答案可能是「用 CSP 自带导航器 + 关掉它的多余交互」，**这不需要任何插件**。而如果诉求是「在 CSP 窗口内嵌一个我自己的实时预览」，官方没有任何接口支持 —— 除非 Celsys 未来开放新 SDK，否则该需求在「不抓屏」的前提下无解。

### 功能 B：一键灰度

**判定：可行（核心交付功能），但有必须提前说明的范围限制。**

**能做的：**

| 需求点 | 可行性 | 说明 |
|---|---|---|
| 对当前选中图层灰度化 | 可行 | 滤镜作用于宿主交给它的目标图层 |
| 保持透明区域不变 | 可行 | 只改 RGB 不改 Alpha 即可；官方商店插件说明反证了「可控制是否改 Alpha」 |
| 支持合理撤销 | 可行 | CSP 撤销栈对外部滤镜结果为一次操作；此外可在滤镜内提供「不修改原图」的预览确认流程 |
| 非破坏性 | **部分** | 滤镜最终是**破坏性写回**图层像素。要做到非破坏，只能靠「执行前自动/提示复制图层」或「依赖 CSP 撤销」 |

**做不到 / 有限制的（必须写进用户手册，不允许静默失败）：**

| 需求点 | 结论 | 原因 |
|---|---|---|
| 「当前画布的全部图层」一键灰度 | **做不到** | 滤镜一次只处理一个目标图层，SDK 无图层枚举与批量执行能力。若要做到，只能靠用户在 CSP 里逐层执行，或改用 CSP 自带功能（见下） |
| 文件夹图层整体灰度 | **做不到（作为插件）** | 需要图层树与文件夹合成权，SDK 未开放 |
| 文字图层 / 特殊图层（对白框、透视尺、3D、图像素材等） | **预计不支持**，需真机逐类验证 | 官方商店插件的措辞集中在「ラスターレイヤー」（栅格图层）。具体哪些图层能调起滤镜、哪些报错，**必须真机验证**，我不会凭推测写「支持」 |

**更可靠的替代（我更推荐，且不需要插件）：** CSP 自带「图层属性 / 颜色模式」与「编辑 → 色调校正」等原生能力，可以在不写一行代码的情况下把图层变为灰度，并且有原生撤销与非破坏选项（如新建校正图层）。**如果目标是「稳定可靠地一键灰度」，原生功能 + CSP 的自动动作/快捷键，可能比我做的滤镜插件更稳。**

这一点我必须如实说：为了「做插件」而做插件，会让你得到一个比 CSP 原生更弱、且带破坏性的方案。所以我建议的做法是 ① 我先做 REDcoLAB 灰度滤镜（满足你要的可控算法与集成），② 同时在手册里并列写出「原生做法」，让你按需选择。

### 功能 C：独立叠加剪切蒙版

**判定：不可行 —— 当前技术路线无法实现，暂停开发。**

**你要的层级（A ← B 原生剪切 ← C 用 REDcoLAB 剪切 ← D 再剪切到 C）需要的能力：**

| 需要的能力 | SDK 是否提供 | 证据 |
|---|---|---|
| 枚举/读取图层树 | 否 | §3 全部证据 |
| 读取或设置「用下一个图层剪切」开关与目标 | 否 | 同上；且你自己的要求第 2 条也不允许改原生剪切状态 |
| 创建/组合蒙版 | 否 | 同上 |
| 感知混合模式 | 否 | 同上 |
| 在画布上叠加显示「自定义剪切关系」标记 | 否 | 插件无 UI 叠加/画布绘制权限 |
| 监听图层增删以维护关系 | 否 | 无事件通知接口 |

**我不接受的替代方案（因为属于你禁止的「冒充」）：**

- 用普通文件夹假装嵌套剪切；
- 用图层合并或「预先烘焙好的图像」假装独立的运行时剪切关系；
- 用一次性的滤镜把结果烤进像素，然后声称「建立了剪切关系」。

这些都做不到「关系存在、可编辑、图层改动后仍有效」这几条硬指标，我不会拿它们冒充完成。

**尚存的、合规但不确定的边角可能（【推测】，未验证，不作为承诺）：** CSP 的 `.clip` 文件是包含图层数据的容器，社区有非官方工具能读取其中图层名与栅格图，说明**文件层面**存储了图层结构与部分属性。理论上存在「离线改写 `.clip` 图层关系」的路径，但它 ① 依赖非官方逆向的文件格式知识，随时可能被 CSP 版本变更打破；② 只能在保存后的文件上操作，无法作用于正在编辑的画布；③ 属于「非公开接口」，与你的技术原则冲突。**我不建议走，也不会未经你同意去走。**

### 功能 D：REDcoLAB 统一控制面板

**判定：部分可行。**

| 需求点 | 可行性 | 说明 |
|---|---|---|
| 统一的功能开关与参数界面 | **可行（受限形态）** | 只能做成「滤镜执行时弹出的模态对话框」，以及/或者在 CSP 的「滤镜」菜单下用不同滤镜项分组 |
| 常驻面板 / 停靠面板（贴近工具属性面板的体验） | **不可行** | SDK 无此类 UI 容器。**不允许**把独立窗口冒充成原生停靠面板 |
| 菜单命令入口 | 可行（以滤镜项形式出现） | 每个滤镜会出现在滤镜菜单/滤镜库中 |
| 快捷键 | **不可行（插件侧）** | 插件不能注册快捷键；只能由你在 CSP 的快捷键/修饰键设置里给「滤镜」分配 |
| 设置保存与重启恢复 | 可行 | 插件 DLL 可在自身目录写配置文件（需在文档中说明写在哪里、如何清理） |
| 展示功能状态/错误/不支持能力 | 可行 | 在对话框内显示；同时写进用户手册 |
| 不重复 CSP 原生功能 | 由设计保证 | 我会按此原则裁剪 UI |

**结论：我会实现「一个滤镜对话框 + 一个设置文件」，并在文档里写明它为什么不是停靠面板。**

## 5. 许可与分发约束（必须你知情）

【官方确认】SDK 使用许可契约书关键条款（原文要点翻译）：

| 条 | 内容 | 对你的影响 |
|---|---|---|
| 第 2 条 | 许可范围仅限：开发插件 + **自ら使用**（自己使用）+ 依第 4 条提供给「插件使用者」 | 自己用，完全没问题 |
| 第 4 条 | 要把插件提供给别人，必须**按 Celsys 指定方式提交**（含插件本体与参考资料），**经 Celsys 确认规格**后方可提供；Celsys 有权不批准 | **不能随便把 `.cpm` 发到群里/网盘/GitHub** |
| 第 8 条第 6 项 | 除第 4 条规定的方法外，不得向插件使用者提供插件 | 同上 |
| 第 8 条第 1 项 | 不得用 SDK 开发「独自または派生の開発ツール」（自研或派生的开发工具） | **不能基于 SDK 做「插件开发框架」再分发给别人** |
| 第 5 条 | 插件著作权归开发者；但 **SDK 头文件的著作权归 Celsys** | 源码可以自己留，但**公开源码时不能包含 SDK 头文件**（第三方开发者博客亦得出同一结论） |
| 第 11 条 | 保密义务 | 不要把 SDK 内容当资料散发 |

**实践结论：**

1. **自己开发、自己用** —— 无阻碍。
2. **要把插件给别人（含发给朋友、发到网上）** —— 必须先走 Celsys 流程。**在你明确要求并确认之前，我不会做任何分发动作**（不打包发布、不上传、不建公开仓库）。
3. **源码公开** —— 必须把 Celsys 头文件排除在外，只发布我自己的代码，并说明「需自行从官网获取 SDK 才能构建」。这一点我会直接设计进项目结构（SDK 目录与源码目录分离 + `.gitignore`）。
