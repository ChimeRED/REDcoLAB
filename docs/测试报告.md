### 真机加载的原始证据

证据文件：`docs/evidence/realmachine-product-load.log`

```
[init] hostVersion=6 (apiResult=0) required=1
[init] module registered, version=1.0.0, moduleKind=0x4380
[terminate] module released
[init] hostVersion=6 (apiResult=0) required=1
[init] module registered, version=1.0.0, moduleKind=0x4380
[filterInit] registered filter, targets=RGB/Gray/Binarization, version=1.0.0
```

**为什么这是真机的证据**：`hostVersion=6` 是真实 CSP 5.0.4 的宿主版本，
而我们的模拟宿主固定报告 `hostVersion=1`。两者不可能混淆。
`filterInit registered filter` 证明 CSP 接受了分类名、滤镜名、预览开关与目标图层类型。

**注意**：CSP 会**加载插件两次** —— 第一次只做模块初始化后立即终止，第二次才注册滤镜。
这是 CSP 的正常行为，不是错误。

### ⚠️ 本报告此前的一个错误结论已撤回

本报告先前版本曾记录「两个候选位置均未被加载」。**该结论错误，已撤回。**

根因：CSP 进程继承了 DSH 会话的 `TEMP` 环境变量，探针日志被写进沙箱私有目录
（`%LOCALAPPDATA%\Temp\dsh-*\`），而我一直检查真实用户 `%TEMP%`，因此看不到日志。
详见 `docs/真机取证结论.md` 的更正章节。

`propertyService.createProc` / `addItemProc` / `setIntegerValueProc`、

## 3. 测试过程中发现并修复的真实缺陷

| # | 缺陷 | 现象 | 根因 | 处置 |
|---|---|---|---|---|
| 1 | 未判空宿主回调（**执行阶段**） | 模拟宿主 `filterRun` 阶段 `access violation writing 0x0` | 新实现直接调用 `TriglavPlugInFilterRunIsAlphaLocked`，而该宿主没有提供此回调，解引用空函数指针 | 新增滤镜执行阶段的宿主调用守卫。记录见 `ERR-20261015-001` |
| 2 | 未判空宿主回调（**初始化阶段**） | `filterInitialize` 阶段 `access violation writing 0x0` | 第 1 项只补了执行阶段，初始化阶段仍有 8 处直接调用宿主函数指针（`addItemProc`、`setInteger*`、`releaseProc` 及全部 `TriglavPlugInFilterInitializeSet*` 宏） | 新增 `PropertyServiceUsable` 前置校验 + 完整 `CallProperty*` / `CallSetFilter*` 守卫层。记录见 `ERR-20261015-003` |
| 3 | PowerShell 5.1 编码 | 校验器误报 `no frontmatter`；`.ps1` 自身语法报错 | PS 5.1 按系统 ANSI 代码页读取 UTF-8 文件，中文变乱码且乱码字节含引号，破坏正则与语法 | 脚本改纯 ASCII；读 UTF-8 文件显式指定编码。记录见 `ERR-20261015-002` |
| 4 | 测试替身字符串传递 | `moduleID` / 菜单名读成 `None` | 新建的测试替身未沿用可用的句柄式字符串传递方式 | 改为句柄表方式，`str_of` 正确解析 |
| 5 | 测试替身断言与参数时序错误 | ① 误判透明像素为失败；② `--expect-algorithm` 完全无效（8 个算法输出相同） | ① 断言把「alpha=0 按设计跳过」当失败；② 参数在 `filterInitialize` **之前**写入，被插件注册时的默认值覆盖 | 断言拆为两条；参数改到 `filterInitialize` 之后、`filterRun` 之前写入，与 CSP 真实时序一致 |
| 6 | 最小宿主测试设计错误 | 首版最小宿主剥掉了**必需**回调 `getHostVersionProc` | 把必需回调当成可选回调剥离 | 保留必需回调，只剥离真正的可选回调；插件对版本 API 失败/版本过低明确拒绝加载 |

> 第 1、2 条是**真实的健壮性缺陷**，不只是测试问题：同样的调用在真实 CSP 里如果宿主没提供该回调，
> 会直接导致 CSP 崩溃。旧版之所以没暴露它们，只是因为它恰好没调用那些回调 —— 那是运气，不是正确性。
>
> 第 2 条的教训更深一层：我把「加守卫」当成了一次性局部修补，而不是**贯穿全部宿主交互的规则**，
> 结果同类问题换了个位置又出现一次。现已改为规则并写入 `plugin-dev` Skill 的核心不变量。
